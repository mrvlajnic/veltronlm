# EXP-0007 — Pretraining canary calibration

**Date:** 2026-09-30
**Status:** COMPLETE after two false failures

## Question

How should the pre-training canary be designed so it catches wiring bugs without failing on
correct code?

## Result

Three designs:

| Design | `micro` result | Verdict |
|---|---|---|
| 256 windows, 1024 tokens, 60 steps, batch 1 | 8.768 → 7.214 (1.22x) | **false failure** |
| 32 windows, 1024 tokens, 120 steps, batch 1 | 8.74 → 6.29 (1.39x) | **false failure** |
| **32 windows, 128 tokens, 200 steps, batch 8, lr 2e-3** | **8.216 → 1.861 (4.4x)** | **pass** |

## Interpretation

The first two designs failed for different reasons, and both failures are instructive:

* **Design 1 sampled widely across the corpus.** It was measuring generalisation, not
  wiring. Generalisation is far too noisy at 60 steps to act as a gate.
* **Design 2 used full-length 1024-token windows.** A 55M model barely moves in 120 steps at
  batch 1 over long sequences. Truncating to 128-token windows lets the batch grow, which
  makes the check both meaningful and cheap.

The final threshold is `best_loss < 0.25 x first_loss` with all 200 losses finite. Batch
size is derived from a memory probe (logit tensor ≤ 96 MiB) because a fixed batch of 8 at
1024 tokens OOMs a 12 GiB card.

## Why this matters

The canary's job is to refuse to start when gradients are broken, labels are misaligned or a
shard is corrupt — all of which train without error and produce fluent nonsense. It cost
~90 seconds and saved the failed runs above.
