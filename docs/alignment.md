# Preference Alignment (DPO)

Entry point: `python -m veltron.finetuning.cli dpo --init checkpoints/sft-support`

---

## 1. What is being aligned

Alignment is only meaningful if it targets **measured** failure modes. So the preference
pairs are built from the six failure modes the support system is explicitly designed to
catch, which makes the objective literally "do these things less often" — checkable before
and after.

| Failure mode | Rejected response | What it teaches |
|---|---|---|
| `ungrounded_policy` | Confident answer containing a specific number absent from the retrieved context | Don't invent policy, price or deadline |
| `fabricated_citation` | Cites `[n]` beyond the number retrieved | Don't fabricate sources |
| `false_refusal` | Refuses a question the documentation plainly answers | Refusing everything is also a failure |
| `verbose_padding` | Correct answer buried in pleasantries | Be concise |
| `prompt_leak` | Reveals the system prompt | Never disclose instructions |
| `wrong_product` | Confuses VeltronSense with VeltronHub | Use the right product |

`false_refusal` is the one usually omitted and the one that matters most in production: a
support assistant that always escalates is safe and useless.

## 2. The `chosen` response

With a generator loaded, `chosen` is the model's **own** grounded greedy answer, produced by
running the real RAG pipeline at temperature 0.2 and validating the citations. The preference
set therefore aligns *behaviour* rather than importing a foreign style.

Without a generator, `chosen` is extractive from the chunk, which still yields a valid if
easier signal.

## 3. The objective

DPO (Rafailov et al., 2023):

```
L = -log sigmoid( beta * [ (log pi(yw|x)/pi_ref(yw|x)) - (log pi(yl|x)/pi_ref(yl|x)) ] )
```

Only response tokens are scored. Including prompt tokens would let a pair "win" because the
rejected response had an unusual prompt rendering rather than a worse answer.

`encode_pair` truncates the **prompt**, never the response, for the same reason SFT does.

### 3.1 The reference model

A frozen `copy.deepcopy` of the policy at initialisation, held on the same device with
`requires_grad_(False)`. Because the reference is frozen and the policy comes from a
checkpoint, loading it is a matter of copying tensors — **no second inference pass is
needed at any point**, which is what makes DPO affordable on this hardware.

### 3.2 Diagnostics

Two numbers decide whether a run did anything:

| Metric | Meaning |
|---|---|
| `preference_accuracy` | fraction of held-out pairs where the policy ranks `chosen` above `rejected` |
| `reward_margin` | mean `beta * (logits)` over held-out pairs |

`summary.json` records `baseline`, `final`, `accuracy_delta`, `margin_delta` and an explicit
`interpretation` string. If accuracy does not improve, the run reports:

> "No measurable improvement on held-out pairs; this run did not demonstrate an alignment
> effect and must not be reported as one."

That sentence is in the code, not just in this document.

## 4. Verified properties

| Test | Assertion |
|---|---|
| `test_dpo_prefers_the_chosen_response` | A clearly better pair incurs loss < log 2, accuracy 1.0, margin > 0 |
| `test_dpo_loss_is_minimal_when_preferences_are_matched` | A tie is lower loss than an inverted preference, and reports accuracy 0.0 (a tie is not a win) |
| `test_preference_rejectors_produce_distinct_rejections` | Each rejector produces output, and `fabricated_citation` returns `None` for a valid citation |

The last one matters: a rejector that fires on correct answers would train the model to
avoid good behaviour.

## 5. Guardrails

| Guard | Implementation |
|---|---|
| Non-finite gradients | Detected before the optimiser step; the update is skipped and counted |
| Gradient clipping | 1.0 |
| Low learning rate | 5e-7 (100x below SFT) |
| Reference frozen | `requires_grad_(False)`, `.eval()` |
| No silent success claims | `improved` boolean plus an explicit interpretation string |

## 6. Limitations

1. **No DPO run has completed on this host yet.** The objective is implemented and
   unit-verified; no alignment result is claimed.
2. **Preference pairs are synthetic**, generated by rules from knowledge-base chunks. They
   encode *designed* failure modes, not observed ones from real traffic.
3. **No real teacher model.** `chosen` is the model's own output, so DPO can sharpen existing
   behaviour but cannot import capability.
4. **600 preference pairs at most** from 45 chunks. Too few for a large effect.
5. **No human preference data.** Human evaluation is a designed interface, not a run.
6. **`beta` was not swept.** 0.1 is the standard default.
7. **KL is implicit only.** DPO's implicit reward can drift without a hard KL constraint;
   no divergence monitoring beyond the logged margin.
8. **No reward model.** `ORPO` and reward-model approaches are not implemented.
